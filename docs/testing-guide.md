# Практикум по тестированию фронтенда

Сначала попробуй действия руками в приложении. Отправь пустую форму, затем добавь задачу, отметь её галочкой и переключись между фильтрами «Активные» и «Выполненные». Перезагрузи страницу и проверь галочку. Теперь эти проверки можно повторить в коде.

В файлах тестов `it` задаёт один сценарий, `describe` собирает связанные сценарии в группу, а `expect` формулирует ожидаемый результат. Читай название теста как короткое обещание о поведении приложения.

Окружение определяет, где выполняется код. **Node.js** запускает JavaScript вне браузера и подходит для проверки функций. **jsdom** добавляет в Node.js DOM — дерево элементов страницы — и часть браузерных API, включая `localStorage`. **Chromium** открывает приложение как полноценный браузер. В первых трёх уроках тестами управляет Vitest, в четвёртом — Playwright. [Окружения Vitest](https://vitest.dev/guide/environment.html), [браузеры Playwright](https://playwright.dev/docs/browsers).

## 01. Юнит-тест чистой функции

Код в [tasks.js](../src/tasks.js), примеры в [tasks.test.js](../src/tasks.test.js).

```sh
npm test -- src/tasks.test.js
```

В `package.json` команда `npm test` запускает `vitest run`. Разделитель `--` передаёт путь к файлу в Vitest, чтобы запустить только этот урок.

`validateTitle` получает строку и возвращает объект с очищенным названием или ошибкой. `getVisibleTasks` выбирает задачи для текущего фильтра. Обе функции можно вызвать прямо в тесте. Node.js достаточно, потому что им нужны только переданные аргументы.

Разбери первый тест по схеме Arrange → Act → Assert.

1. **Arrange (подготовка).** Создай строку с пробелами по краям.
2. **Act (действие).** Передай строку в `validateTitle`.
3. **Assert (проверка).** Сравни возвращённый объект с ожидаемым. `toEqual` сравнивает содержимое объектов.

В `it.each` одна и та же проверка запускается для нескольких наборов данных. Тесты с 80 и 81 символом проверяют обе стороны границы.

**Попробуй увидеть падение.** Временно замени `const title = rawTitle.trim()` на `const title = rawTitle` и снова запусти файл. В первом упавшем тесте сравни ожидаемое название с полученным. Затем верни `trim()` и убедись, что тесты снова проходят.

## 02. Тест React-компонента

Код в [TaskForm.jsx](../src/TaskForm.jsx), примеры в [TaskForm.test.jsx](../src/TaskForm.test.jsx).

```sh
npm test -- src/TaskForm.test.jsx
```

Строка `@vitest-environment jsdom` включает jsdom только для этого файла. React Testing Library монтирует форму через `render`, а `screen` ищет элементы в DOM. Роль — это назначение элемента, например `textbox` для текстового поля. Доступное имя помогает отличить одно поле от другого. У поля «Новая задача» оно берётся из `label`, чей `htmlFor` совпадает с `id` поля.

- `userEvent.setup()` создаёт объект, через который тест имитирует печать и клики. `async` позволяет использовать `await` внутри сценария. Дождись завершения действия, прежде чем проверять результат.
- `vi.fn()` создаёт функцию, которая записывает вызовы. В этом примере она заменяет родительский обработчик `onAdd`. Так можно проверить, какое название форма передала наружу.
- `jest-dom` добавляет к `expect` проверки DOM вроде `toHaveValue`. `cleanup()` убирает смонтированные компоненты, чтобы следующий тест начал с пустой страницы. Обе настройки находятся в [testSetup.js](../src/testSetup.js).

**Попробуй сам.** Напиши тест для 81 символа. После отправки формы проверь, что появилось сообщение о лимите, поле сохранило введённое значение, а `onAdd` не был вызван.

## 03. Интеграционный тест

Код в [App.jsx](../src/App.jsx), примеры в [App.test.jsx](../src/App.test.jsx).

```sh
npm test -- src/App.test.jsx
```

Здесь `render(<App />)` монтирует форму и список вместе. Нажатие «Добавить» вызывает настоящий обработчик. Тест проверяет появление задачи, галочку, счётчик и результат фильтрации. `beforeEach` подключает хранилище jsdom и задаёт пустой список, чтобы тесты можно было запускать отдельно и в любом порядке. `afterEach` восстанавливает исходное окружение.

`localStorage` хранит данные по ключам и принимает строковые значения. Поэтому перед сохранением `JSON.stringify` превращает массив задач в строку, а при следующем открытии страницы `JSON.parse` восстанавливает массив. В тесте загрузки важно записать данные **до** `render`, потому что `App` читает хранилище при создании состояния.

При поиске элемента в Testing Library выбери метод по ожидаемому результату.

- `getByRole` — элемент должен быть на странице прямо сейчас. Если его нет, поиск выдаст ошибку.
- `queryByRole` — элемент может отсутствовать. Метод вернёт `null`, и можно проверить исчезновение через `not.toBeInTheDocument()`.
- `findByRole` — элемент появится позже, например после запроса. Вызов нужно ожидать через `await`. В этом приложении для текущих проверок достаточно дождаться действий пользователя.

**Попробуй сам.** Создай отдельный тест со стартовой выполненной задачей. Сними галочку, проверь уменьшение счётчика и убедись, что задача видна в фильтре «Активные». В качестве примера подготовки данных возьми тест, который загружает задачу из хранилища.

## 04. Сквозной тест в Chromium

Сценарий в [tasks.spec.js](../e2e/tasks.spec.js), настройка сервера в [playwright.config.js](../playwright.config.js).

**Chromium** — браузер с открытым исходным кодом, на котором основан Google Chrome. **Playwright** управляет браузером из теста. Он открывает страницу через HTTP, заполняет форму и перезагружает вкладку. Так проверка проходит через реальную загрузку страницы и настоящее хранилище браузера. [Проект Chromium](https://www.chromium.org/Home/), [браузеры Playwright](https://playwright.dev/docs/browsers).

```sh
npx playwright install chromium
npm run test:e2e
```

Первая команда скачивает сборку браузера для установленной версии Playwright. Вторая запускает тесты. Playwright сам поднимает Vite на `http://127.0.0.1:4173`. По умолчанию Chromium запускается в режиме **headless**, то есть без видимого окна. Если хочешь увидеть окно браузера, запусти `npm run test:e2e -- --headed`. [Запуск тестов Playwright](https://playwright.dev/docs/running-tests), [настройка локального сервера](https://playwright.dev/docs/test-webserver).

Каждый тест получает вкладку `page` в отдельной браузерной сессии со своим `localStorage`. Тест вводит название, отправляет форму клавишей Enter, ставит галочку и перезагружает страницу. `page.getByRole` возвращает **локатор** — описание того, как найти элемент. Он находит задачу при действии или проверке и может найти её заново после перезагрузки. Проверка `await expect(task).toBeChecked()` повторяется до выполнения условия или истечения времени ожидания. [Локаторы](https://playwright.dev/docs/locators), [проверки Playwright](https://playwright.dev/docs/test-assertions).

**Посмотри шаги.** Запусти `npm run test:e2e:ui`, выбери сценарий в боковой панели и запусти его. Затем щёлкни по шагу в списке действий, чтобы посмотреть состояние страницы на этом шаге.

**Попробуй сам.** Добавь проверку, что после перезагрузки название задачи появляется ровно один раз. Для этого у локатора есть проверка `toHaveCount(1)`.

## Самостоятельная задача

Добавь кнопку «Удалить выполненные». Сначала опиши поведение в интеграционном тесте. Подготовь активную и выполненную задачи, нажми кнопку и проверь, что осталась только активная, а счётчик показывает «Выполнено 0 из 1».

Запусти тест и прочитай причину падения. Затем реализуй кнопку, добейся прохождения и запусти остальные тесты. Если после этого упростишь код, повтори проверки. Так выглядит цикл «красный → зелёный → рефакторинг».
